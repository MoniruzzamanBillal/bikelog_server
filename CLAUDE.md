### Environment

See `ENV_SETUP.md` for the full table. Two things that bite:

- **`DATABASE_URL` must be a real Neon host.** `src/app/lib/prisma.ts` uses the `PrismaNeon` adapter, which connects over a WebSocket — pointing it at a local Postgres fails on the first query with an opaque `ErrorEvent`, not a clean connection error. Use a Neon branch for local dev.
- **Migrations use a different variable.** `prisma.config.ts` points the migration engine at **`DATABASE_URL_UNPOOLED`** (direct/unpooled), while the runtime client uses the pooled `DATABASE_URL`. Schema work needs both set.

`MONGO_DATABASE_URL` is still read by `src/app/config/index.ts` but is vestigial post-migration.

Write `.env` entries as `KEY=value` with **no spaces around the `=`**. The npm `dotenv` package trims whitespace around keys, so `KEY = value` works for `yarn dev` — but Compose's `env_file` parser is a different implementation, and a key arriving as `"JWT_ACCESS_SECRET "` would leave `process.env.JWT_ACCESS_SECRET` undefined and 401 every authenticated request while the container still reported healthy. `.env.example` is the committed template.

### Docker (spec 47)

```bash
docker compose up local -d --build          # builds and serves on :5000
docker compose exec local yarn db:migrate   # migrations are MANUAL, never on startup
```

Four things to know:

- **There is no `postgres` service and there never should be.** The `PrismaNeon` adapter cannot talk to a local Postgres (see above), so the container reads `DATABASE_URL` and connects to the real Neon host. No volumes either — nothing writes to the filesystem at runtime.
- **Migrations are deliberately not run on container start.** No entrypoint script, no `migrate deploy` in `CMD`. This project applies migrations by hand and `deploy.yml` doesn't run them either; `prisma/` and `prisma.config.ts` ship in the image only so the `exec` above works. `npx prisma migrate status` is the read-only version.
- **`ENV PORT=5000` is load-bearing.** `src/app/config/index.ts` reads `process.env.PORT` with no fallback, so `app.listen(undefined)` would bind a random ephemeral port, log `listening from port undefined`, and leave the container green but unreachable. Pinned in both the Dockerfile and compose.
- **The healthcheck is liveness-only.** `GET /` returns 200 without touching the database, and `server.ts` only `console.log`s a `$connect()` failure — so a container with a broken `DATABASE_URL` reports healthy while every data route 500s. Prove the DB separately; a login attempt with a bogus email returning a real `404` is enough.

Base image is `node:22-slim` rather than alpine because `bcrypt` (a dead dependency — nothing in `src/` imports it; only `argon2` is used) has no musl prebuild and would pull a `python3 make g++` toolchain into the build. `openssl` is installed in both the `deps` and `runner` stages: `prisma migrate` runs in the runner and warns about an undetectable libssl version without it. `TZ` is pinned to `Asia/Dhaka` because `spending.service.ts` and `mileageRecord.service.ts` bucket months in **local** time, which would shift under the container's default UTC.

## Architecture at a glance

- **Module-per-feature** under `src/app/modules/<domain>/`: `.route.ts` / `.controller.ts` / `.service.ts` / `.interface.ts` / `.validation.ts` (`.constant.ts` where an `as const` enum is needed). There are **no `.model.ts` files** — the data model lives in `prisma/schema.prisma`. New modules register in `src/app/router/index.ts`'s `routeArray`. Nested-resource modules use `Router({ mergeParams: true })` since they mount under `/bikes/:bikeId/...`; `maintenanceLog.route.ts` and `errorLog.route.ts` each uniquely export **two** routers from one module.
- **Ids are application-generated Mongo-format ObjectIds — this is the migration's load-bearing decision.** Every model is `id String @id` with **no `@default`**; services call `generateObjectId()` (`src/app/util/generateObjectId.ts`, backed by `bson-objectid`) to mint a 24-char hex id on create. This preserved every historical id through the Phase 8 cutover and keeps FK integrity. Never add `@default(uuid())`/`cuid()` to an existing model.
- **The wire contract is deliberately still Mongo-shaped — this is why both clients needed zero changes.** Each service maps Prisma rows back before returning: `id` → `_id`, scalar FK columns → their old populated-field names (`bikeId` → `bike`, `maintenanceTypeId` → `maintenanceType`, `oilTypeId` → `oilType`, `ownerId` → `owner`), and **Prisma `Decimal` → `Number()`** (clients cannot consume a Decimal object). See the `toApi`-style mapper at the top of `fuelLog.service.ts` for the canonical shape. Any new field must go through the same mapping, or clients will silently read `undefined`.
- **Soft delete is now explicit, not automatic.** Mongoose's `pre("find")`/`pre("findOne")` hooks are gone and Prisma has no equivalent here — **every query against a soft-deletable model must pass `isDeleted: false` in its own `where`**. This applies to `user`, `bike`, `fuelLog`, `maintenanceLog`, `bikeIssue`, `bikeAccessory`, **and both catalogs (`maintenanceType`, `engineOilType`) since spec 41 added soft delete to them**. Only derived data (`mileageRecord`) has none. Forgetting the clause is the single easiest way to leak deleted rows.
- **The two catalogs are per-user, not global (spec 46).** `MaintenanceType` and `EngineOilType` each carry a required `ownerId` with `@@unique([ownerId, name])`, so **every** query against them needs **both** `ownerId: <req.user.userId>` and `isDeleted: false`. Ownership is enforced in the service layer by `findOwnedMaintenanceTypeOrThrow` / `findOwnedEngineOilTypeOrThrow` (`<module>.utils.ts`), each a mirror of `findOwnedBikeOrThrow`: a cross-user id returns **404**, not 403, collapsing "no such id" / "soft-deleted" / "someone else's" into one indistinguishable path. `ownerId` is deliberately absent from both Zod schemas and both `T*` types — it comes from the JWT, never the body; adding it would reintroduce the IDOR through the front door. The composite unique deliberately covers soft-deleted rows (no partial index on `isDeleted`), which is what keeps spec 41's revive-by-name path load-bearing. A brand-new user's catalogs are **empty** — there is no seeding. `MaintenanceType.requiresOilType` replaced the clients' `name === "Engine Oil"` gate on the oil-type dropdown. **Names (spec 50):** trimmed and non-empty in the Zod schemas, and a case-variant of one of the owner's *live* names is a 409 (`findLiveNameConflict` in each `<module>.utils.ts`); revive-by-name matches ignoring case, takes the newly typed casing and keeps the row id. Those lookups are raw `lower(name) = lower($1)` on purpose — Prisma's `mode: "insensitive"` compiles to `ILIKE` on PostgreSQL, so `_`/`%` in a name behave as wildcards (`A_C` falsely collides with `ABC`); don't "simplify" them back. There is no DB constraint behind the case-insensitive rule, and legacy case-variant duplicates were left in place.
- **`maintenanceLog.service.ts`'s `catalogInclude` deliberately filters on neither `isDeleted` nor `ownerId`** — a historical log must still resolve the name of a since-deleted type (spec 41 §B), and after spec 46 a log's catalog rows are owner-coherent by construction. Adding either filter is the tempting wrong move and would re-break the bug spec 41 fixed.
- **Auth**: JWT bearer via `authCheck`. Authorization is ownership-based (`Bike.ownerId` against `req.user.userId`), checked in the service layer via the shared `findOwnedBikeOrThrow` helper (`bike.utils.ts`) — `authCheck` only verifies the token, it does not check ownership. Passwords hashed with **`argon2`**, not `bcrypt` (both are deps; `argon2` is what's wired up, now in `user.services.ts` rather than a model hook). `userRole` (`admin`/`user`) **is** enforced now, but only on the `errorLog` admin routes; there is no promotion endpoint — making an admin is a direct DB write, by documented convention.
- **Errors/responses**: throw `AppError(status, message)`, let `globalErrorHandler` format it; controllers use `catchAsync` + `sendResponse(res, { status, success, message, data })` — the key is `status`, **not** `statusCode`.
- **Prisma error handling is service-local, and `globalErrorHandler` has stale branches.** Unique-constraint violations are caught per-service as `Prisma.PrismaClientKnownRequestError` + `code === "P2002"` → a clean 409 (`user.services.ts`, `maintenanceType.service.ts`, `engineOilType.service.ts`). `globalErrorHandler.ts` still branches on three Mongo-era conditions that **can no longer fire** (`error.name === "ValidationError"`, `"CastError"`, `error.code === 11000`) and has no central Prisma branch, so `P2003` (FK) and `P2025` (not found) fall through to a generic 500. Catch those locally where they matter.
- **List endpoints use `buildPrismaListQuery`** (`src/app/builder/buildPrismaListQuery.ts`) — the Prisma replacement for the old chainable builder, preserving the exact `sort`/`limit`/`page`/equality-filter query contract. It deliberately drops `.search()` (nothing wired a `searchTerm`) and Mongoose's `-__v` field default. It splits `sort` on comma *or* whitespace, since some callers pass Mongoose-style space-separated multi-field sorts. Used by `fuelLog`, `maintenanceLog`, `bikeIssue`, `bikeDocument`, `errorLog`.
- **Ownership-scoping replaces the old IDOR query-stripping pattern.** Under Mongoose, nested list endpoints had to strip `bike`/`isDeleted` from `req.query` because a second `.find()` merged last-write-wins. `buildPrismaListQuery` instead composes a `baseWhere` that the caller controls, so a rogue `?bike=<otherId>` can no longer override the ownership scope. Still pass ownership through `baseWhere` and never interpolate raw query params into it.
- **Aggregation convention (non-default, deliberate)**: monthly/yearly/lifetime mileage and spending stats are computed via plain `findMany()` over a date range plus JS `filter()`/`reduce()` — **never** SQL/Prisma `groupBy` aggregates. This is house style (see `context/architecture.md`), not an oversight. Averages are computed **client-side** — the API returns totals only.
- **Event date vs. `createdAt`**: `FuelLog.date` / `MaintenanceLog.serviceDate` are user-editable and are what aggregations must bucket by — entries get back-logged, so `createdAt` would misfile them into the wrong month. Spec 40 added `createdAt` only as a *tie-breaker* for list ordering. **Date sanity rules:** a fuel log's `date` and a maintenance log's `serviceDate` can't precede the bike's `purchaseDate` (400, equal is allowed; for maintenance the omitted-means-now default is checked too), and `purchaseDate` itself can't be more than 24 h in the future (the slack is because `"YYYY-MM-DD"` parses as midnight UTC). Moving a bike's `purchaseDate` later than its existing logs is still allowed.
- **`Bike.initialOdometer` vs. `currentOdometer`**: `initialOdometer` is an immutable snapshot taken at bike creation; `currentOdometer` is denormalized and only ever moves upward — via `bumpOdometerIfHigher` (`bike.utils.ts`) when a fuel/maintenance log is saved, or via the manual `PATCH /bikes/:id/odometer` endpoint (spec 44, which rejects lower values with a 400). Editing a fuel or maintenance log's `odometerReading` bumps it too (specs 48/49). **Every odometer input is bounded `finite().nonnegative().max(999999)`** (manual endpoint, fuel logs, maintenance logs) — `z.number()` alone accepts `Infinity` (raw JSON `1e999`), which Postgres stores and which then wedges the bike for good because nothing lowers `currentOdometer`; new odometer-bearing fields need the same bound. **Fuel-log readings must be non-decreasing in *date* order** across the bike's live fuel logs (`assertOdometerInSequence` in `fuelLog.service.ts`; floor is `initialOdometer`, equal readings allowed, soft-deleted logs ignored, same-timestamp ties count as earlier). It is deliberately **not** compared with `currentOdometer`: backdated entry is a supported flow (spec 26) and manual/maintenance updates raise `currentOdometer` while nothing can lower it (DEF-12), so that comparison would permanently block fuel logging after one typo. A full-tank fill with 0 km since the last one saves the log but writes **no** `MileageRecord` (`mileageRecordClosed: null`). Anchor "the bike's starting point" math on `initialOdometer`, never `currentOdometer` — the latter may already have been mutated by the very log being processed (a real bug fixed post-implementation).
- **`ai` module (spec 16)**: three endpoints under `/bikes/:bikeId/ai` — `GET /spending-insight`, `GET /mileage-insight` (both cached by relevant log *count*, not a TTL; a bike with zero logs short-circuits to a fixed message and never calls the AI), and `POST /chat` (stateless per request, client resends history; `ai.validation.ts` rejects a client-supplied `role: "system"`, context capped to the 20 most recent fuel + 20 most recent maintenance logs, plus retrieved manual chunks per spec 18). All three funnel through `askOpenRouter` in `src/app/util/openRouterClient.ts` — the **single choke point** every AI feature must use, which tries `FREE_MODELS` in order and throws `503` only if all fail. Don't call the `openai` SDK directly from a service; add models to `FREE_MODELS` instead.
- **Uploads**: `src/app/middleware/upload.ts`'s `upload` multer instance is hardcoded image-only and streams straight to Cloudinary, so `req.file` only ever has `{path, filename}` — never local bytes. PDF routes (specs 18/19) that need raw content use their own memory-storage instance plus `uploadRawBuffer`/`uploadDocumentBuffer` in `src/app/util/cloudinary.ts`; don't mutate `upload` to fit a new case. `deleteCloudinaryImage(publicId)` is best-effort catch-and-log — a failed delete shouldn't block the caller's own action.
- **Outbound `expenseTracker2` sync (spec 30)**: `notifyExpenseTracker` (`src/app/util/expenseTrackerClient.ts`, summaries in `transactionRequestSummary.ts`) posts fuel-log creates, maintenance-log creates, and accessory `pending`→`purchased` transitions to a **different project** as a *pending review item* — never a real transaction. Fire-and-forget: never awaited, never blocks or fails this server's response; failures log via `errorLog` with no retry queue. Needs `EXPENSE_TRACKER_BASE_URL` + `EXPENSE_TRACKER_INTEGRATION_KEY`. An accessory created directly as `purchased` does **not** sync.
- **Cron routes bypass `authCheck` by design** — `/api/cron/weekly-summary` (`notification`) and `/api/cron/cleanup-error-logs` (`errorLog`) are protected by an `x-cron-secret` header instead, matched against `CRON_SECRET`. Both are driven by GitHub Actions workflows, not Vercel Cron. The daily error-log cleanup exists because Postgres has no equivalent to Mongo's TTL-index sweep.
- **Dead code — don't import, don't confuse**: `src/app/builder/Queryuilder.ts` (the old Mongoose builder, now unreferenced; note the class name really is `Queryuilder`, not `QueryBuilder`) and `src/app/helper/openRouter.ts` (superseded by `util/openRouterClient.ts`).
- **`mongoose` is still an installed dependency and still imported by three files** — `builder/Queryuilder.ts` (dead) and `Error/handleValidationError.ts` + `Error/handleCatError.ts` (both still wired into `globalErrorHandler.ts`). It was four until spec 46 §H **deleted `scripts/migratePhase8MongoToPostgres.ts`**: that script's first action was an unconditional `deleteMany({})` on both catalog tables, which against the per-user schema would have raised `P2003` on `maintenance_types` and — worse — *silently nulled every log's `oilTypeId`*, since that FK is `ON DELETE SET NULL`. The Mongo cutover finished 2026-09-15; the file is recoverable from git history. Removing the dependency is still **not** a one-line change; it requires retiring the three remaining files first. `server.ts` also retains the commented-out `mongoose.connect()` boot path above the live `prisma.$connect()` one.
- **Unused deps** — don't build on these: `bcrypt`, `nodemailer`.
- **`dist/` is checked into git but goes stale** — not regenerated automatically, and still contains modules deleted from `src/` back in spec 01. Never treat it as source of truth; run `yarn build` if you need it current.
- **Deployment**: Vercel serverless (`vercel.json` → `dist/server.js`), auto-deployed by `.github/workflows/deploy.yml` on push to `master`. The Prisma client is cached on `globalThis` across invocations in non-production. Reminders are computed on-read, not by a background job.
